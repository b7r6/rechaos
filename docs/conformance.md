# REAPI conformance scorecard

`scripts/conformance_report.py` points a fixed, deterministic battery of
black-box probes at a single Remote Execution API (REAPI) / remote-build
endpoint and emits a graded correctness report as both JSON
(`scorecard.json`) and a readable Markdown report (`scorecard.md`).

Where [`scripts/fleet-stress.py`](../scripts/fleet-stress.py) hunts for faults
under concurrency and [`scripts/consistency_oracle.py`](../scripts/consistency_oracle.py)
checks a recorded history against a formal model, the scorecard answers a
simpler, procurement-shaped question: *point it at an endpoint and tell me how
correct it is.*

## Running it

Run under `nix develop` (needs `grpcio` plus the generated Python bindings under
`.build/python`, generated by `scripts/test.sh`):

```sh
nix develop --command python3 scripts/conformance_report.py \
  --endpoint 127.0.0.1:50052 --instance main --out ./scorecard-run
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `--endpoint` | `127.0.0.1:50052` | `host:port` of the REAPI/RBE endpoint. Configurable; nothing is hardcoded. |
| `--instance` | `main` | REAPI instance name. |
| `--seed` | `20261002` | Deterministic seed for probe blob contents. |
| `--out` | *(required)* | Output directory; `scorecard.json` and `scorecard.md` are written here. |

A compact one-line JSON summary is printed to stdout for CI logs. The process
exits `0` whenever the battery ran to completion (regardless of grade), so it is
safe to use as an evidence generator; gate on the `grade.letter` field in the
JSON instead of the exit code.

### Determinism

Blob contents are a pure function of `(--seed, label)` via SHAKE-256 and the
probe order is fixed. Responses and dependent checks can still vary with server
state, scheduling, eviction, and transport errors, so the report is not guaranteed
byte-identical across runs. Preserve the observations as evidence.

## What is probed

Each probe produces one or more **checks**. A check has a stable `id`, a
`category`, a `status`, a one-line `detail`, and structured `evidence`.

### Check statuses

| Status | Meaning | Counts toward grade? |
| --- | --- | --- |
| `PASS` | The probe observed the expected behavior for its tested case. | Yes (numerator + denominator) |
| `FAIL` | The server implements the method but violates the spec. | Yes (denominator only) |
| `UNSUPPORTED` | The method is not implemented here (UNIMPLEMENTED / HTTP/2 404). | No |
| `SKIP` | Could not be evaluated: a transport fault (UNAVAILABLE / DEADLINE_EXCEEDED), or a dependency check did not run. | No |

The `UNSUPPORTED` vs `FAIL` distinction is deliberate and load-bearing: an
absent *optional* method is a capability gap, not a correctness defect, and must
not lower the grade. A `FAIL` is reserved for a method that is present and wrong.

### The checks

| Category | Check id | What it verifies |
| --- | --- | --- |
| Capability negotiation | `cap.get` | `Capabilities.GetCapabilities` responds; records advertised digest functions, max batch size, AC-update capability, API version range. UNSUPPORTED if not implemented. |
| Capability negotiation | `cap.digests` | When Capabilities is present, at least one digest function is advertised. |
| Content-addressable storage | `cas.write` | `ByteStream.Write` accepts a well-formed upload and commits exactly the declared byte count. |
| Content-addressable storage | `cas.read` | `ByteStream.Read` returns the uploaded bytes intact (round-trip). |
| Content-addressable storage | `digest.sha256` | SHA256 support — from the advertised set if Capabilities is present, otherwise inferred from the successful CAS round-trip. |
| Content-addressable storage | `cas.fmb` | `FindMissingBlobs` reports exactly the absent blob and omits the present one. |
| ByteStream semantics | `bs.committed` | The `committed_size` from `Write` matches the declared size and agrees with `QueryWriteStatus`. |
| ByteStream semantics | `bs.qws` | `QueryWriteStatus` on a finished upload reports `complete` with the exact committed size. A missing retained upload status is inconclusive. |
| ByteStream semantics | `bs.range` | Range reads are correct across whole / prefix / suffix / interior / **at-EOF** / **limit-past-EOF** cases. A read at `read_offset == size` must succeed with zero bytes. |
| ByteStream semantics | `bs.short` | A client that declares size N but finishes after fewer than N bytes is **rejected** (INVALID_ARGUMENT / FAILED_PRECONDITION / DATA_LOSS), never silently accepted. |
| Content-addressing integrity | `integrity.write` | Bytes that do **not** hash to the declared digest are either rejected on write or at minimum never served back under the claimed digest. This is the core content-addressing guarantee. |
| Action cache | `ac.update` | After uploading the required Command and Action, `UpdateActionResult` returns an equivalent `ActionResult`. UNSUPPORTED if the method is absent. |
| Action cache | `ac.get` | `GetActionResult` round-trips the stored `ActionResult`. |
| Batch operations | `batch.update` | `BatchUpdateBlobs` stores several small blobs with per-entry OK status. |
| Batch operations | `batch.read` | `BatchReadBlobs` round-trips those blobs. |
| Batch operations | `batch.limit` | `max_batch_total_size_bytes` is advertised (from Capabilities). UNSUPPORTED when Capabilities is absent. |

## Outputs

### `scorecard.json`

Structured, machine-readable. Top-level fields:

- `endpoint`, `instance`, `seed`, `generatedAt` — run identity.
- `grade` — `{ letter, passed, failed, graded, passRatio, integrityFailed, integrityCapApplied }`.
- `consistency` — `{ level, reason, signals }` (see below).
- `statusCounts` — count of checks by status.
- `featureMatrix` — one row per notable method with a `support` classification.
- `categories` — every check grouped by category, with full `evidence`.

### `scorecard.md`

A readable report: header with grade, consistency, and status counts; the
feature-support matrix; checks grouped by category; and a pointer back to this
rubric.

## Grading rubric

The overall grade is computed only from `PASS`/`FAIL` checks. `UNSUPPORTED` and
`SKIP` are excluded from the denominator.

Let `ratio = passed / (passed + failed)` over graded checks:

| Ratio | Letter |
| --- | --- |
| ≥ 0.97 | A |
| ≥ 0.90 | B |
| ≥ 0.80 | C |
| ≥ 0.65 | D |
| < 0.65 | F |

Two special cases:

- **Integrity cap.** Any `FAIL` in the *Content-addressing integrity* category
  caps the grade at **D** (if it would otherwise have been A/B/C). Content
  addressing is the one property whose violation makes a store unsafe regardless
  of how much else is correct: if the server will serve bytes that do not hash
  to the digest you asked for, no amount of passing range-read checks redeems it.
  The JSON exposes `integrityCapApplied: true` when this happens.
- **Nothing gradable.** If no check produced a `PASS` or `FAIL` (for example the
  endpoint was unreachable and every probe `SKIP`ped), the grade is `N/A` with
  `passRatio: null`, so callers can distinguish *could not test* from *tested and
  failed*.

## Inferred consistency level

The scorecard reports a coarse, explainable consistency classification. This is
**not** a linearizability proof. To check a finite recorded history against an
explicit register model, use
[`consistency_oracle.py`](consistency-oracle.md). It is a conservative mapping
from observed guarantees to a level:

| Level | Condition |
| --- | --- |
| `content-addressed` | CAS round-trip passes, integrity passes, and `FindMissingBlobs` passes. |
| `read-your-writes` | CAS round-trip passes (you can read back what you wrote) but integrity fails or `FindMissingBlobs` was not confirmed. |
| `unknown` | The CAS round-trip did not pass, so nothing stronger can be claimed. |

The `signals` object records the three booleans the level is derived from, so
the classification is always auditable from the report itself.

## Scope and non-goals

- **Black-box only.** No server source imports, configuration edits, or
  restarts. Everything is a public gRPC call.
- **Not a load or chaos test.** Timing is excluded from the graded output; for
  fault-injection and concurrency campaigns use `fleet-stress.py`, and for
  history-level linearizability use `consistency_oracle.py`.
- **Not exhaustive.** The battery covers the high-value correctness surface
  (content addressing, ByteStream semantics, AC, batch, capability negotiation);
  it is intentionally small enough to run fast and reason about completely.

The local contract suite exercises the full battery against a verifying fixture
and includes regressions for unrelated corrupt readback bytes, transport errors
that must remain inconclusive, and required Action/Command uploads. A graded
PASS remains evidence for the specific checked fields and workload.
