# Scheduler chaos: the fleet rig, scenario steps, and shrinking a scheduler bug

The gateway (`rechaos serve`) sits between a build client and one endpoint and
can tear what crosses that wire. It cannot express the failures that live in a
scheduler with a fleet behind it: a large action starved by a stream of small
ones, a worker whose input cache evicts a file as it is being staged, a
scheduler store that refuses a worker's result so the record stays `EXECUTING`
indefinitely. This page documents the path rechaos has for those: a local fleet
rig, a scenario step list as the witness, a step engine with a pure invariant
evaluator, the chaos monkey mode that composes scenarios cold, and
`rechaos minimize --steps` to shrink what it finds.

Everything here is black-box. The rig starts unmodified NativeLink processes
from generated configs; the engine speaks REAPI and, for control-plane faults,
plain Redis commands and POSIX signals to processes the rig owns.

## The pieces

| Piece | File | What it does |
|---|---|---|
| Fleet rig | [`scripts/fleet_rig.py`](../scripts/fleet_rig.py) | Starts one scheduler process (CAS, AC, execution, `worker_api`) and N worker processes, each with its own fast-tier input cache and `cpu_count`/`memory_kb` platform properties; optionally a Redis the scheduler stores its state in. Writes `rig.json`. |
| Scenario steps | JSONL, see below | The witness: actions with properties, inputs, timing, and detach behavior, plus control-plane faults. |
| Step engine | [`scripts/scheduler_steps.py`](../scripts/scheduler_steps.py) | Replays steps against a rig, records per-action stage timings, evaluates invariants 8-13 as a pure function of the observations, and acts as the minimize checker. |
| Monkey mode | [`scripts/chaos-monkey.py`](../scripts/chaos-monkey.py) `--rig` | Composes random scenarios from the dimensions the rig offers, runs them, and freezes each finding with a `minimize.sh`. |
| Shrinker | `rechaos minimize --steps` | The same delta-debugger as for fault timelines, over opaque steps ([`Rechaos.Core.Shrink`](../src/Rechaos/Core/Shrink.hs), [`Rechaos.Shell.Steps`](../src/Rechaos/Shell/Steps.hs)). |

## The rig

```sh
NATIVELINK_BIN=/path/to/nativelink python3 scripts/fleet_rig.py up \
  --backend redis --workers 3 --slots 4 --memory-kb 20480 \
  --worker-cache-bytes 8000000 --out runs/rig --detach
python3 scripts/fleet_rig.py status  runs/rig/rig.json   # processes alive, health route answers
python3 scripts/fleet_rig.py restart runs/rig/rig.json   # same shape, same ports, empty state
python3 scripts/fleet_rig.py down    runs/rig/rig.json
```

The rig is stdlib-only and generates its NativeLink configs from parameters
(`fleet_rig.py config ...` prints them). Workers reach the CAS and AC over gRPC
on the scheduler process and register over `worker_api`, so they are genuinely
separate processes that can be paused individually. Each worker's fast-tier
filesystem store has `max_bytes = --worker-cache-bytes`; that is the knob the
eviction race needs.

`rig.json` records the backend, ports, per-worker `slots`/`memory_kb`/cache
size, the scheduler timeouts, every pid, the NativeLink binary and its SHA-256,
and the full parameter set, so `restart` rebuilds an identical fleet and a
frozen finding names exactly what it ran on.

**Redis backend.** NativeLink's Redis scheduler backend needs the RediSearch
module (`FT.CREATE`). A plain `redis-server` has none, so with `--backend redis`
the rig loads one: `--redis-module PATH`, or the default `auto`, which takes
`$REDIS_SEARCH_MODULE`, then a cached `.build/redis-modules/redisearch.so`,
then extracts the module from the official `redis:8` image with `docker`. A
nixpkgs `redis-server` also needs the legacy `libcrypt.so.1` ABI and
`libstdc++` on `LD_LIBRARY_PATH` for that module; `auto` resolves both from
nixpkgs (`--redis-ld-path` or `$REDIS_MODULE_LD_PATH` override). Redis runs
with `maxmemory-policy noeviction`, the configuration under which a full store
refuses writes instead of silently dropping scheduler state. The rig records
the Redis server's own pid (not a wrapper's) so a `store-pause` freezes the
right process.

**Object-store CAS.** `--cas-backend azure` or `--cas-backend s3` makes the
scheduler's CAS a `fast_slow` store whose fast tier is tiny
(`--cas-fast-bytes`, 1 MB) and whose slow tier is NativeLink's own cloud
client, pointed at the dialect fault proxy
([`s3_fault_proxy.py`](../scripts/s3_fault_proxy.py) with `--dialect` and a
control port) in front of a local emulator: Azurite (account SAS generated by
the rig, so the store is keyless, as a SAS-only deployment is) or MinIO (throwaway
root credentials, bucket created with a SigV4 request). Both come from nixpkgs
on first use, or from `$AZURITE_BLOB_BIN` / `$MINIO_BIN`; `--s3-endpoint`
points the S3 dialect at an endpoint you control instead. The client's retrier
is the rig's default retrier (`--store-retries 6 --store-retry-delay 0.3
--store-retry-jitter 0.5`, about 38 s of backoff before the client gives up). GCS has a dialect in the proxy but no rig: this
NativeLink's GCS client has no endpoint override outside its tests.

**What the rig cannot do.** NativeLink 1.7 and later exposes no Prometheus endpoint
(OTLP only), so the monkey's metric-based detectors (invariant 7, the soak
tracker) have no data on a rig; invariants 8-13 do not need them. The rig is
local only.

## Scenario steps (the witness)

A scenario is JSON Lines, one object per step. Only integers are shrinkable;
`at_ms` offsets are from the scenario's start.

```json
{"step":"blob","id":"tool0","bytes":400000,"weaker":{"bytes":1}}
{"step":"action","id":"s000","at_ms":0,"cpu":1,"memory_kb":2048,"sleep_ms":2000,"inputs":["tool0","u000"],"detach":false,"weaker":{"sleep_ms":0}}
{"step":"action","id":"L0","at_ms":3000,"cpu":1,"memory_kb":16384,"sleep_ms":500,"inputs":[],"weaker":{"sleep_ms":0}}
{"step":"store-full","at_ms":1200,"for_ms":6000,"weaker":{"for_ms":100}}
```

| Step | Fields | Effect |
|---|---|---|
| `blob` | `id`, `bytes`, `executable` | A deterministic input blob (content derived from a per-run nonce and the id), uploaded to the CAS before the scenario starts. `executable: true` stages it through the worker's executable "variant" path, which is what toolchain binaries take. |
| `action` | `id`, `at_ms`, `cpu`, `memory_kb`, `sleep_ms`, `inputs` (blob ids), `detach`, `timeout_ms` | At `at_ms`, `Execute` an action whose command is `/bin/sh -c 'sleep <sleep_ms>'` (see "Worker-side commands" below), with `cpu_count`/`memory_kb` platform properties and the named inputs in its root. `detach: true` cancels the `Execute` stream at the first `EXECUTING` and re-attaches later with `WaitExecution`. Inputs naming a deleted `blob` step are dropped, so deleting a blob means removing that input everywhere. |
| `store-full` | `at_ms`, `for_ms` | Cap the scheduler's Redis `maxmemory` at its current `used_memory` for `for_ms` (every further write is refused with `OOM`), then restore. Needs a Redis-backed rig. |
| `store-pause` | `at_ms`, `for_ms` | `SIGSTOP` the Redis server for `for_ms` (a failover window), then `SIGCONT`. Needs a Redis-backed rig. |
| `worker-pause` | `at_ms`, `for_ms`, `worker` | `SIGSTOP` one worker process for `for_ms`, then `SIGCONT`. |
| `store-throttle` | `at_ms`, `for_ms`, `ops` | Switch the object-store fault proxy's sustained throttle on for the named operations (default `GET`), in the rig's dialect shape, then off. Needs `--cas-backend azure|s3`, and a scheduler `max_action_executing_timeout_s` of 0 or at least `for_ms` (otherwise the scenario is inconclusive: that timeout would requeue fetching actions on its own clock). |

`weaker` is the shrinker's intensity declaration: a map from an integer field of
the same step to the floor it may shrink toward. Each intensity candidate moves
one field halfway to its floor (`floor + (value - floor) / 2`), so the chain is
finite, strictly decreasing, and reaches the floor. The reader in
`Rechaos.Shell.Steps` is fail-closed: a `weaker` that is not an object of
non-negative integers, names an absent or non-integer field, or declares a
floor above the current value rejects the file with its line number. The step
engine validates the rest (unknown kinds, control steps a memory-backed rig
cannot serve, worker indexes) and makes such a run inconclusive rather than a
verdict.

## Authoring scenarios and fleets in Dhall

The JSONL above is the wire form. The typed source of truth is `dhall/`:

| File | Defines |
|---|---|
| [`dhall/Step.dhall`](../dhall/Step.dhall) | The `Step` union (`Blob`, `Action`, `StoreFull`, `StorePause`, `WorkerPause`, `StoreThrottle`), each a closed record, with `render` to the wire shape and constructors (`blob`, `tool`, `action`, `detached`, `storeFull`, `storeThrottle`, ...) carrying the usual floors. |
| [`dhall/Floors.dhall`](../dhall/Floors.dhall) | The intensity declaration, one closed record per step kind (`Floors.Action::{ sleep_ms = Some 0 }`): a floor for a field the kind does not have is a type error. |
| [`dhall/Op.dhall`](../dhall/Op.dhall) | The throttle's operation vocabulary (`GET`, `PUT`, `DELETE`, `HEAD`, `LIST`), exactly what the proxy's control endpoint accepts. |
| [`dhall/Scenario.dhall`](../dhall/Scenario.dhall) | A scenario as `List Step.Type`, its `render` to the array the readers accept, and `range` and `each` so a stream of actions is one expression. |
| [`dhall/Rig.dhall`](../dhall/Rig.dhall) | The fleet's shape with the same defaults as `fleet_rig.py` (`Rig::{ workers = 3 }`), scheduler backend and CAS backend as unions; launch mechanics (ports, binaries, seeds) are not rig shape. |
| [`dhall/NativeLink.dhall`](../dhall/NativeLink.dhall) | The scheduler and worker configurations as total functions of a rig, the resolved `Ports`, and a state directory. |
| [`dhall/Limits.dhall`](../dhall/Limits.dhall) | The invariant bounds, derived from a rig as `Limits.for_rig` derives them; a step contract compares the two on `dhall/examples/limits.dhall`. |
| [`dhall/examples/`](../dhall/examples) | The four reference scenarios (starvation, eviction, stuck, throttle), two fleet configs, and the limits example. |

What the types buy: a scenario cannot name a step kind the engine does not
know, omit a field a kind needs, carry a negative count or floor, declare a
floor for a field its kind does not have, or throttle an operation the proxy
does not know; a rig cannot set a knob that does not exist. That a floor sits
at or below its value, and that a count is positive where NativeLink needs it
to be, remain reader and runtime checks. What the `dhall` flake check adds on
top: every definition type-checks offline and is `dhall format` clean, every
example scenario renders to a step list `rechaos validate-steps` accepts, and
the rendered fleet configs are equal, as parsed JSON, to what
`scripts/fleet_rig.py config` emits for the same parameters, so the typed
definitions and the Python emitter cannot drift apart.

What it costs, and when a faster implementation would pay, is measured in
[`dhall-cost.md`](dhall-cost.md).

```sh
dhall-to-json --file dhall/examples/scn-starvation.dhall > steps.json   # a JSON array; every reader takes it
rechaos validate-steps steps.json
rechaos minimize --steps steps.json ...                                 # writes JSONL back
```

## The engine and the invariants

```sh
nix develop --command python3 scripts/scheduler_steps.py run \
  --rig runs/rig/rig.json --steps steps.jsonl --out runs/scn --queue-age-ms 5000
```

`run` uploads the blobs and action protos, starts the scenario clock, drives
each action on its own thread and each control step on the main timeline,
re-attaches to detached operations once a second until the executing bound,
checks `FindMissingBlobs` for every server-side failure, writes
`observations.json`, and prints the findings. The observations are the per
action `submit_ms`, first `QUEUED`, first `EXECUTING`, `done_ms`, last stage,
status, message, exit code, operation name, probes, and whether the inputs were
present; plus the control steps with their actual start and end.

The evaluation itself lives in the pure core: `Rechaos.Core.Scenario.evaluate`
(invariants 8 through 13 as a total function of the observations and limits),
exposed as `rechaos evaluate observations.json [--queue-age-ms N]
[--executing-ms N] [--download-budget-ms N]`, which prints the same report
object the engine prints. The Python `evaluate` in `scheduler_steps.py` is the
transitional mirror the driver still calls; a differential contract runs both
over random observations and the named fixtures and requires identical findings
(and the catalog's named cases are among the fixtures), so neither can drift
until the Python one is retired with the rest of the driver.

`evaluate(observations, limits)` is pure and deterministic. The bounds:

| Bound | Source | Used by |
|---|---|---|
| `queue_age_ms` | the scenario: the longest action in its base stream plus a dispatch margin (`--queue-age-ms`) | invariants 8 and 9 |
| `executing_ms` | the rig: `max_action_executing_timeout_s + worker_timeout_s` plus 5 s (`--executing-ms` overrides) | invariant 10 |
| `workers`, `slots`, `memory_kb` | the rig | invariant 9's capacity model |
| `download_budget_ms` | the rig: the worker's `max_download_timeout_s` (`--download-budget-ms` overrides) | invariants 12 and 13 |

Time an action spends inside any control-fault window (`store-full`,
`store-pause`, `worker-pause`, `store-throttle`, from the step's actual start
to its actual end) is discounted from the queue-age and executing bounds. A
fault's direct effect is not a scheduler decision; what the invariants measure
is what the scheduler does outside and after the fault, such as a record that
stays `EXECUTING` long after the store is writable again. Invariants 12 and 13
additionally look inside a `store-throttle` window on purpose, because giving
up or re-dispatching while the store says "retry later" is the behavior under
test.

An overtake counts only when the later submission was
dispatched at least one second ahead, so a sub-second ordering wobble among
actions that all waited for the same slot is not starvation.

The invariants and their signatures are catalogued as entries 8-13 in
[`invariants.md`](invariants.md): `queue-starvation`, `dispatch-stall`,
`stuck-executing`, `input-evicted-failure` (and the catch-all
`action-failed-inputs-present:<CODE>`), `store-throttle-giveup`,
`store-throttle-redispatch`. The observations also carry the proxy's per-key
request counts (`store`) when the rig has an object-store CAS.

### Worker-side commands

Every command a scenario executes runs on the *worker*, which need not be an
FHS host: a NixOS worker has no `/bin/true` or `/bin/sleep`, and an action
naming one "completes" with exit 127 without exercising anything (11.7k such
completions on one Azure soak node in a day). The scenarios therefore assume
only what every REAPI worker ships, `/bin/sh` (NativeLink's own examples assume
it too): the monkey's `--execution` scenarios run `/bin/sh -c true` (`true` is a
shell builtin, so no `PATH` is needed) and the step engine's `action` runs
`/bin/sh -c 'sleep N'` with an explicit `PATH` covering NixOS and FHS layouts
(`scheduler_steps.WORKER_PATH`). No path is resolved on the controller and
shipped to the worker. Both are constant for a run, so an action's digest
varies only with its salt and the step's own fields.

## The monkey's scheduler mode

```sh
nix develop --command python3 scripts/chaos-monkey.py --rig runs/rig/rig.json --only-scheduler
```

With `--rig` the monkey takes host, port, and instance from the manifest and
adds a `scheduler` mode (or runs only it with `--only-scheduler`). Each
iteration composes a scenario from these dimensions, every one drawn through
the feedback-guided chooser, so nothing tells the monkey which combination
reproduces which failure class:

- a base stream of small actions: spacing, duration, `memory_kb`, and a count of
  two to six fleets' worth, capped at about twenty seconds of stream;
- zero to two large actions asking for 50%, 75%, or 90% of a worker's memory,
  submitted once the stream has saturated the fleet;
- input cache pressure: none, mild (shared inputs at 50% of the worker cache plus
  10% per action), or heavy (80% plus 20%);
- a control-plane fault: none, `worker-pause`, on a Redis rig `store-full` or
  `store-pause`, for 2, 5, or 10 seconds somewhere in the first half of the
  stream, and on an object-store rig `store-throttle` for 20, 45, or 70 seconds
  (capped at the scheduler's executing timeout when one is set), which also
  forces at least mild cache pressure so there are inputs to fetch;
- the share of actions that detach their client (0%, 50%, 100%);
- trailing probes: after the stream and any fault, one small action per slot,
  so a fleet that silently lost capacity shows up as `dispatch-stall`.

The queue-age bound is the stream's action duration plus three seconds. The
scenario is written to the iteration directory as `steps.jsonl` before it runs.

A first finding of each signature freezes, under
`corpus/<signature>/`: `finding.json`, `steps.jsonl`, `observations.json`,
`scenario.json` (the knobs and limits), `rig.json` (the fleet), and
`minimize.sh`.

## Shrinking a finding

`minimize.sh` is the whole recipe; it needs the rig's NativeLink binary to still
exist (the manifest names it) and the rechaos dev shell for the Python checker:

```sh
RECHAOS_BIN=./result/bin/rechaos sh runs/monkey/<run>/corpus/queue-starvation/minimize.sh
```

which expands to

```sh
rechaos minimize --steps corpus/queue-starvation/steps.jsonl --output corpus/queue-starvation/minimal.jsonl \
  --signature queue-starvation --repetitions 2 --trial-timeout <scenario + bounds + 60s> --max-trials 400 \
  --check "python3 scripts/scheduler_steps.py check --rig corpus/queue-starvation/rig.json \
           --signature queue-starvation --fresh --queue-age-ms N --executing-ms M --settle-ms S --download-budget-ms D"
```

The checker restarts the fleet with empty state before every trial (`--fresh`),
replays `$RECHAOS_STEPS`, evaluates with the frozen limits, and writes
`triggers` only when the exact signature is among the findings. A trial whose
rig was unhealthy, whose steps the rig cannot serve, or whose checker died is
`Unknown` to the minimizer and never advances the witness, so a flaky trial
cannot be promoted to the minimal cause. The output is deletion-1-minimal under
the same contract as a fault timeline (`status: "complete"`); each retained step
is one the failure needs.

Trials are slow by nature: one scenario plus a rig restart per trial, typically
thirty to sixty seconds. Budget for it with `--max-trials` and prefer shrinking
the smallest frozen scenario for a signature.

Two operational facts about `--fresh`. It takes over the fleet that the frozen
`rig.json` names (it stops those processes and starts identical ones on the
same ports, refreshing the manifest), so it must not run while a monkey is
using that rig; and the last trial's fleet is left running for inspection,
`fleet_rig.py down` stops it. The rig signals a process only after checking
that its pid still belongs to the process the rig started (the manifest
records each process's kernel start time), so a manifest frozen days ago can
never stop or pause a process that merely reused the pid; a mismatch makes the
step, or the restart, inconclusive instead.

## What this catches, by failure class

| Failure class | Trigger the monkey draws | Signature | Pre-fix (upstream v1.7.6) | Post-fix (upstream `main`, see below) |
|---|---|---|---|---|
| Lost result on a full scheduler Redis; record stays `EXECUTING`; nothing re-checks without a client | `store-full` (or `store-pause`) during a stream with detached clients | `stuck-executing` | Reproduced: the actions whose results arrived during the `OOM` window stayed `EXECUTING` for the whole bound while later work ran | Quiet: the refused results were resent and every action completed |
| Worker disk cache at 99.9%: hard-link fails between lookup and staging | heavy cache pressure with shared inputs on a small `--worker-cache-bytes` | `input-evicted-failure` | Reproduced: `FAILED_PRECONDITION ... file was likely evicted from cache` with every input present in the CAS | Quiet: 32 of 32 actions `OK` on the same 3 MB cache |
| Large actions starving behind small ones | one or two large actions after the stream saturates the fleet | `queue-starvation` | Reproduced: an action asking for 80% of a worker's memory waited 2x its bound while 35 later submissions ran | Still fires with the default config; quiet with `--reservation-hold-after-s 2` (the #2933 hold is opt-in) |
| Idle workers whose slots look taken after a store failure | trailing probes after any fault | `dispatch-stall` | Not observed (the probes ran) | Not observed |
| Object store throttling reads (Azure `503 ServerBusy`), client giving up well inside the download budget, re-dispatch re-downloading the same inputs | `store-throttle` for 20 to 70 s on an Azure or S3 rig | `store-throttle-giveup`, `store-throttle-redispatch` | Reproduced on upstream v1.7.6: Azure gives up at 36 s (`Failed to start download from Azure ... On attempt 7`) and re-dispatches at 20 s intervals; S3 re-dispatches and ends the client stream with `INTERNAL` | Quiet: all twelve actions completed two seconds after a 60 s throttle lifted, after 480 throttled reads |

NativeLink's upstream fixes for these rows are #2923 and #2925 (lost
result), #2926 and #2928 (eviction race), #2931 and #2932 (throttle), and
#2933 (reservation hold), all in v1.7.7 and later. The pre-fix column ran
against an upstream v1.7.6 release build (`b5bdf36a`, three commits past the
tag); the post-fix column ran the identical scenario files against upstream
`main` at `0fd9cd26`, which has all seven merged. The same step files produce
the signatures on the former and none on the latter, which is the evidence
that the detectors measure the bugs and not the bounds. Every number in the
table is from one run of the committed scenario files on one workstation; the
frozen `runs/` evidence is not committed. The rig takes any binary through
`NATIVELINK_BIN` or `--nativelink`; `--reservation-hold-after-s` emits the
`reservation_hold` option, which a pre-v1.7.7 binary rejects as an unknown
field.

## Limits of the claims

- The invariants are timing-based with explicit bounds. A bound set below what
  a correct scheduler needs produces a finding that is true of the bound, not
  of the scheduler; the defaults (an action's duration plus three seconds;
  the scheduler's own executing timeout plus its worker timeout plus five
  seconds) are chosen so a correct scheduler has slack.
- Invariant 9's capacity model uses declared `cpu_count` and `memory_kb` only;
  a worker with a lower `max_inflight_tasks` than its slots would make a stall
  finding spurious, so the rig does not set one unless asked.
- The rig is a loopback fleet. It reproduces the scheduler's decisions, not a
  cluster's network, autoscaler, or object store.
- A scenario is deterministic in what it asks for, not in what the scheduler
  does with it; the shrinker's `--repetitions` and `Unknown` handling are what
  make a minimized witness trustworthy.
